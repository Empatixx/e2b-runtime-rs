E2B starts most sandboxes by **resuming a snapshot**: the orchestrator loads a paused microVM and hands it to the SDK. That step decides how long a user waits. We rewrote the orchestrator in Rust with the same API, and this post compares its resume time with the Go original.

## Summary

- One sandbox at a time: **Rust p50 51 ms, Go p50 321 ms**. Rust stays between 33 and 63 ms.
- Four in parallel: **Rust p50 121 ms, Go p50 430 ms**.
- Eight in parallel on 4 vCPUs: **Rust p50 277 ms, Go p50 747 ms**. The Rust tail grows here (p90 713 ms).
- Guest RAM size barely matters: a 512 MiB template gives almost the same numbers as 1 GiB.

## Method

| | |
|---|---|
| Node | Azure `Standard_E4ds_v4`: 4 vCPUs, 32 GB RAM, Ubuntu 24.04, host kernel 6.17. A nested KVM guest, not bare metal. |
| Host setup | As upstream requires: udev `nowatch` rule for `nbd*`, `nbds_max=128`, 16 GiB of hugepages |
| Firecracker | `v1.14-0.2.0`, the E2B fork, guest kernel `vmlinux-6.1.158` |
| Template | `e2bdev/base`, built by Go `create-build` with its optimize phase, 2 vCPUs, 1 GiB or 512 MiB |
| Rust | `resume_bench` example: the real node and gRPC server, `Create` with `snapshot: true`, then delete and wait until Firecracker and the NBD device are gone |
| Go | `resume-build -iterations N`, which calls the sandbox factory directly; we added a parallel mode for this test |
| Runs | 40 sequential, 48 with 4 or 8 in parallel, for each implementation and template |

P99 comes from 40 to 48 runs, so it is close to the maximum.

All times in milliseconds. One Rust resume splits like this: Firecracker spawn and NBD in parallel 13 to 23 ms, snapshot load 6 to 16 ms, vCPU resume and MMDS 1 to 8 ms, envd `/init` 6 to 28 ms.

## What made the difference

Most of these changes bring Rust in line with what Go already does.

- **2 MiB huge pages** for the guest memory: about 60 page faults per resume instead of about 7000.
- **The chunk cache is read through an mmap**, like Go. A page fault installs its page straight from the mapping. Before, each 2 MiB block was copied up to five times.
- **Prefetch starts copying pages while the snapshot loads**, as soon as Firecracker connects to the memory server.
- **Firecracker is started inside its cgroup** with `clone3(CLONE_INTO_CGROUP)`, as Go does. Moving it there afterwards cost 3 to 7 ms and sometimes 250 ms.
- **`TCP_NODELAY` on the gRPC port**. Go turns it on for every connection. Without it, every `Create` reply waited 40 ms for a delayed ACK.
- **The udev `nowatch` rule** for NBD devices, which upstream requires on its nodes.

## What did not work

We ported Go's **NBD over generic netlink** and measured it. A connect right after a device was released waits 100 to 250 ms inside the kernel, in `blk_mq_freeze_queue_wait`. Go hits the same wait, and it explains most of its 320 ms runs. The older ioctl connect takes about 17 ms, so Rust keeps it.

## Known gaps

- The node is a nested VM with 4 vCPUs. We expect lower numbers for both on bare metal and have not measured that yet.
- At 8 parallel resumes on 4 vCPUs, the Rust tail grows. We have not found the cause yet.
- Go runs without its gRPC layer and Rust with it, so the comparison slightly favours Go.
- Go maps the whole guest memory from hugepages at resume. With the 4 GiB that upstream's guide reserves, 8 parallel 1 GiB sandboxes failed in 15 of 48 Go runs. Rust did not fail.

The numbers and the setup are in [`docs/performance-resume.md`](https://github.com/Empatixx/e2b-runtime-rs/blob/main/docs/performance-resume.md), and the Rust benchmark is [`resume_bench.rs`](https://github.com/Empatixx/e2b-runtime-rs/blob/main/crates/orchestrator/examples/resume_bench.rs).
